V3-9112-001 — RFC 9112 §2.2

Conformant Normative level: MUST

Requirement
An HTTP/1.1 sender MUST generate messages conforming to the HTTP-message grammar and use the protocol version appropriate to that syntax.
Conditions
Version-specific sender conditions in RFC 9112 §2.2 apply.
Applicable role
sender
Responsible layer
Node.js HTTP sender; Achieve selects status, fields, and body
Implementation evidence
Node http.Server centrally serializes ordinary responses created at achieve.js:1559-1591; Achieve's fixed CONNECT response template at achieve.js:1255-1264 uses an HTTP/1.1 status line, CRLF field framing, explicit Content-Length, and Connection close.
Test evidence
Batch D byte-level capture validated representative static 200, missing-resource 404, parser 400, HTTP/1.0-request, Content-Length, chunked, field-name, and status-line output. Node rejected attempted invalid field syntax rather than serializing it.
Assessment rationale
For Achieve core output through supported Node response APIs, representative wire checks plus the centralized serializer and fixed direct template support Conformant. This is not an exhaustive proof of every grammar production or arbitrary application socket output.
Open question
Bounded to tested core paths and supported response APIs on Node.js 22.15.0; direct application socket writes remain application responsibility.

V3-9112-002 — RFC 9112 §2.2

Conformant Normative level: MUST

Requirement
An HTTP/1.1 recipient MUST parse messages as an octet sequence in an encoding that is a superset of US-ASCII.
Conditions
Parsing as Unicode without octet boundaries is unsafe.
Applicable role
recipient
Responsible layer
Node.js HTTP parser
Implementation evidence
Requests reach Achieve only after Node's native HTTP parser delineates request lines and fields at achieve.js:1407-1441 and 1559-1591.
Test evidence
A Batch D raw field-value control used octets 0x80, 0xff, 0xc2, and 0x85. Achieve and standalone Node preserved one octet per exposed code unit instead of UTF-8-decoding 0xc2 0x85; a high-bit field-name octet was rejected with 400.
Assessment rationale
The direct controls support octet-oriented parsing for the tested request-line/field parser boundary on Node.js 22.15.0. They do not independently enumerate every request component or future parser implementation.
Open question
Bounded to the tested components and Node.js 22.15.0; runtime parser changes require reassessment.

V3-9112-017 — RFC 9112 §6.1

Nonconformant Normative level: SHOULD

Requirement

Conditions
Apply only under the conditions and exceptions stated in the cited section and summarized in the requirement.
Applicable role
server
Responsible layer
Node.js HTTP parser/Achieve endpoint
Implementation evidence
Node parses Transfer-Encoding before dispatch at achieve.js:1407-1441 and 1559-1591; Achieve has no transfer-coding decoder or registration mechanism.
Test evidence
Batch D sent Transfer-Encoding: frobnicate, chunked with valid chunk framing. Achieve and standalone Node returned 200, removed chunk framing, and delivered the remaining bytes to the application. Assessment rationale
The final-chunked probe isolates the §6.1 recommendation from §6.3's mandatory final-coding rejection. The supported endpoint does not understand or decode frobnicate and no documented reason for departing from the 501 SHOULD was identified.
Open question
This is a SHOULD-level Node-inherited endpoint defect, not a malformed-final-framing result. Reassess on a newer Node parser or if Achieve gains explicit transfer-coding support.
