Achieve RFC 9112 HTTP/1.1 Connections

Created November 6, 2026 · Updated November 6, 2026 · Achieve 3.1.0 · Qualified runtime: Node.js 24.22.2

Requirement levels: The applicable rules include MUST and SHOULD requirements for safe connection reuse, ordered responses, explicit closure, and TLS shutdown.

Achieve uses Node.js connection management while completing each routed request through its static-resource or servlet response path. Persistent connections reduce setup costs, but only when message boundaries and closure signals remain unambiguous.

Applicable requirements

  • MUST: Before reusing a connection, a server must read the complete request body or close the connection (RFC 9112 §9.3).
  • MUST: Responses to pipelined requests must be sent in the same order as the requests (§9.3.2).
  • MUST / SHOULD: A server that receives or sends Connection: close closes after the final response and should send that option when it intends to close (§9.6).
  • MUST / SHOULD: A TLS server must attempt the closure-alert exchange and should tolerate an incomplete client close (§9.8).

Request completion and reuse

Node's HTTP parser delineates each request and owns keep-alive reuse. Achieve's buffered input modes consume their supported request bodies before dispatch completes; streaming applications remain responsible for consuming or deliberately terminating their input. Response completion then leaves Node to serialize the next response on the connection.

HTTP/1.1 pipelining does not make application responses unordered: Node preserves response order even when later requests have already arrived. Achieve does not add a second connection scheduler.

Closing the connection

When either peer selects Connection: close, the tested endpoint completes the final response and does not process another request on that connection. Over TLS, Node and OpenSSL provide the record-layer shutdown. Server-initiated close tests observed close_notify; abrupt client shutdowns did not prevent subsequent connections from being served.

Responsibility and limits

Message parsing, pipelining order, socket reuse, and TLS alerts are runtime responsibilities. Achieve controls whether its own request and response work reaches a clean completion boundary. Application code that takes ownership of a request stream or response must preserve those boundaries.

The verification is bounded rather than a stress or resource-leak proof. It establishes representative sequential, pipelined, close-signaled, incomplete-request, and TLS-close behavior on the qualified runtime. Message-length rules are covered separately in HTTP/1.1 Message Framing.

Verification

Raw TCP and TLS probes inspected response ordering, connection reuse, explicit close behavior, TLS alerts, and recovery after incomplete client shutdown. See the Batch D evidence review.
