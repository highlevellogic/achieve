Achieve RFC 9113 HTTP/2 Prioritization

Created November 6, 2026 · Updated November 6, 2026 · Achieve 3.1.0 · Qualified runtime: Node.js 24.22.2

Requirement levels: RFC 9113 deprecates the RFC 7540 priority-signaling scheme; its remaining guidance includes SHOULD and MAY recommendations.

Achieve does not expose an application-level priority policy or implement a second HTTP/2 scheduler. Node.js and nghttp2 schedule frames and streams beneath Achieve's request/response interface.

Applicable requirements

RFC 9113 §5.3.2 deprecates the earlier priority-signaling scheme. Servers SHOULD use other contextual information when no priority signal is present and MAY interpret total absence as lack of client support. Alternative signaling is defined separately by RFC 9218.

Verified scope

Achieve's source contains no priority configuration, PRIORITY frame parser, or RFC 9218 Priority policy. Frame parsing and outbound scheduling are delegated to Node/nghttp2. Existing flow-control tests show that control frames and independent streams can progress under bounded window conditions, but that does not establish a particular prioritization strategy.

Classification and limits

The conformance ledger does not claim that Achieve applies client priority signals or contextual priority information. No focused evidence establishes how Node.js 24.22.2 schedules competing Achieve responses under different priority signals. That behavior is therefore intentionally left undescribed rather than inferred from ordinary multiplexing tests.

Application guidance

Applications should not rely on an Achieve-specific stream-priority guarantee. Response size, computation order, flow control, client behavior, and the runtime scheduler can all affect completion order even though each response remains attached to its own stream.
